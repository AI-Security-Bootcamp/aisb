Gradient Through Tokens

Every exercise in section 5.2 in pictures, in order. The attack needs the model to say which input tokens would help most. A plain integer lookup cannot answer that. A one-hot selector can, and the output stays identical. The loss scores how strongly the model expects the target text, and a greedy loop turns those scores into a jailbreak suffix.

coordinate
One suffix slot. A full point is a tuple of token ids, such as (91, 91, 91, 91, 91, 91).
where it ends
At the lowest-loss suffix found after T steps. Low loss does not guarantee a jailbreak, so generate and check the reply.
vs gradient descent
Tokens are discrete, so there is no small step to take. The gradient only shortlists swaps to try.
grads
[n, V]. One score per position and candidate token. Only suffix rows are used.
X[i]
The k token ids for slot i with the most negative gradient.
candidates
B copies of the prompt, each with one slot swapped.
x = min(...)
Keep the candidate with the lowest exact loss.
fuzzing view
Step 1 is cheap feedback that guides mutation. Step 3 is real execution that decides what survives.
white-box
Step 1 needs the model weights. Suffixes found this way still transfer to closed models.
token
One input unit, a word piece, stored as an integer id.
embedding table E
Array with one row of numbers per vocabulary entry. The model reads rows, never raw ids.
loss
Attacker's score: how unlikely the model is to open with "Sure, here is...".
gradient
Per-input sensitivity of that score, like coverage feedback that tells a fuzzer which input change mattered.
teacher forcing
The target is fed in as input, so the model never chooses it. One pass scores every target token.
sanity check
" the lazy dog" gives a low loss because the model knows the phrase. " the purple moon" gives a high one.
why it matters
In 5.2.5 the target becomes "Sure, here is..." and this number is what the attack minimizes.
sequence
[before | suffix | after | target]. Same order as the template, with the target appended.
5.2.3 by hand
torch.cat([input_ids, target_ids]), then logits[0, n-1 : -1], then target_ids.
5.2.5 with manager
manager.get_input_ids(suffix_ids), then logits[0, manager.loss_slice], then full[manager.target_slice].
requires_grad_
Marks the one-hot as an input whose gradient PyTorch should keep.
forbidden ids
Special tokens such as end-of-text, which would not survive being typed into a prompt.
truncation error
The second-order and higher terms dropped from the linear estimate. They reorder candidates.
takeaway
The gradient is a cheap filter, not a judge. Execution decides.
greedy
Take the best local improvement each round, never backtrack.
coordinate
Change one suffix slot per round.
delivery caveat
A real attack is a string, so a candidate must decode and re-tokenize to the same ids. The reference code filters for this. Ours does not.
goal
The request, in the reference code.
control
The suffix.
worker
One model.
